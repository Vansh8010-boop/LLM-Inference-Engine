LLM inference engine, built from scratch in PyTorch

Serving Qwen2.5 to many users at once, 2.4× faster than Hugging Face.

My own transformer forward pass, a paged KV cache, a continuous-batching scheduler with preemption, and a streaming OpenAI-compatible API, measured against Hugging Face model.generate() on the same GPU and the same real chat traffic.

How it works

Every step the scheduler rebuilds the batch, and the block manager decides where each sequence's KV cache lives. New requests join the running batch at every step instead of waiting for a batch to finish.

Results

Two features that are correct, and not faster on this hardware

INT8 weights

Quality holds and memory drops, but there is no fast INT8 matmul here: the weights are converted back to FP16 on every call, which costs more than reading half the bytes saves. A fused kernel would turn the saving into speed.

Speculative decoding (0.5B drafts, 1.5B verifies)

The guesses are accepted often, but at batch size 1 both models are limited by kernel-launch overhead, so the 0.5B draft costs about half a 1.5B step instead of a tenth.

What didn't work (and what it taught me)

93 of 100, not 100

My first forward pass matched Hugging Face on 93 of 100 prompts. The other 7 split at near-ties one fp16 step apart. Hugging Face lets SDPA handle grouped-query attention itself, which picks a different kernel than repeating the K/V heads by hand. Matching that made every layer bit-identical.

Batches are never bit-identical

A matmul over 32 rows uses different cuBLAS kernels than one over 1 row, so batched output differs in the last bit. The tests demand exact matches except at genuine near-ties, and check the logit gap at every divergence.

INT8 got smaller, then slower

PyTorch's fused INT8 kernel slows down linearly with the number of rows (70 ms vs 0.6 ms for FP16 at 1,024). Dequantizing per call is faster but still loses to FP16, and scaling after the int8 matmul overflowed fp16 into NaN until the weights were scaled first.

Speculative decoding needs a big target

Correct, with 68% of draft tokens accepted, yet 0.9× speed. Small models at batch size 1 are bound by CPU kernel launches, not GPU math, so the draft is not cheap enough. It pays off with a 7B+ target or CUDA graphs.

The laptop ran out of memory, not the GPU

A model download, a benchmark and the tests at once exhausted Windows commit memory, and a progress bar piped through PowerShell grew one endless line until the shell crashed. The final sweep ran on Kaggle, one job at a time, logging to files.

Reproduce it

Every number on this page is read from data/results.json, exported from the saved result files in the repo.

git clone https://github.com/Vansh8010-boop/LLM-Inference-Engine.git
cd LLM-Inference-Engine
pip install torch --index-url https://download.pytorch.org/whl/cu128
pip install -r requirements.txt
python scripts/download_model.py
python -m pytest tests -v            # exact Hugging Face match, batching, preemption
python -m bench.final_sweep          # every configuration, 3 runs each (~3.5 h on a T4)
python -m bench.make_plots           # charts from bench/results/
python -m bench.export_site_data     # this page's data
